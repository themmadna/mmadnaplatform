# 10 — Playwright Recommendation

## Recommendation: **YES, write a small smoke script.**

Static analysis caught most of what it could catch. The things it can't catch are exactly what users hit in production:

- The Pulse-redesign regressions (`05-ui-ux.md §1`) — I can grep `#D4AF37` but I cannot tell you what the gold-tinted JudgeDirectory looks like on a 360px viewport against the Pulse-tinted bottom nav. A Playwright run with viewport screenshots makes the regression visible.
- Modal focus traps (`06-accessibility.md §1`) — only verifiable with a real keyboard sim. `playwright keyboard.press('Tab')` is the only way to confirm focus stays inside the modal.
- RPC drift at the wire (`02-data-fetching.md §3`) — the doc says no drift, but the doc could be wrong. A smoke run that opens DNA / leaderboard exposes any RPC field rename instantly.
- Mobile viewport rendering — Phase 8 is mobile-first but no live browser test confirms layouts. `playwright --device='iPhone 13'` catches overflow, mis-aligned hit targets, dropped Pulse tokens.
- Runtime crashes — App.js is 1475 lines with many conditional renders. Static lint doesn't catch a `meta.fighter1_name` access on a fight where meta failed to load (already partially mitigated, but historically a recurring bug class).

## Infrastructure cost (honest)

- **Guest flows = cheap.** No auth fixture needed. `goto('/')`, click "Continue as Guest", everything else runs without credentials. Includes voting, search, fight detail, scoring, scorecard reveal, judge directory, judge profile. **Recommend starting here.**
- **Auth flows = moderate.** A `tests/.auth/user.json` storageState file generated by a single auth-login spec, then reused. Requires a dedicated test Supabase user. Worth doing if you want Leaderboard / Judging DNA / "your votes are saved" coverage, but the guest-mode passes already exercise 90% of the rendering logic.

For a first pass: **guest mode only.** Defer auth fixtures until/if it pays off.

## Three flows worth covering

In priority order.

### Flow 1 — Guest can score a historical fight end-to-end ★ highest blast-radius

**Why:** Touches the entire critical path — events list → fight detail → spoiler protection → RoundScoringPanel → ScorecardComparison → judges. If any RPC drifts or component crashes, this catches it.

**Steps:**
1. `goto('/')`, click "Continue as Guest"
2. Click most recent event
3. Click a fight that went to decision
4. Verify spoiler protection card is visible (text "Results Hidden")
5. Score all 3 rounds (click R1 → red 10 → blue 9 → "Lock Round"; repeat R2, R3)
6. Verify spoiler auto-reveals (spoiler card gone, result banner present, "wins via Decision" visible)
7. Click "Judges" tab
8. Verify ScorecardComparison rendered with 3 round rows + at least 1 judge column

**Assertions that catch the highest-blast-radius bugs:**
- No `console.error` in this whole flow (catches the FightDetailView debug logs leaking to production — `03-components.md §C3.1` — they're `console.log`/`console.warn`, so assert no `console.error` for *real* errors).
- After scoring, `[role="status"]` live region or result banner contains "wins" — catches winner-string regression.
- ScorecardComparison renders ≥3 score cells with `aria-label` or visible text matching `^\d{1,2}$` — catches missing judge data joins.
- No layout overflow: page width on iPhone 13 viewport ≤ 430px.
- Pulse-red presence: at least one element with class containing `pulse-red`. Catches a future accidental theme revert.

### Flow 2 — Guest sees Judge Directory and opens a profile ★ catches the Pulse regression

**Why:** This flow lives on the most-regressed surface (`05-ui-ux.md §1`). Adding a visual snapshot test here pins the redesign.

**Steps:**
1. `goto('/')`, dismiss guest banner (or proceed as guest)
2. Tap "Judges" bottom-nav tab
3. Verify judge directory list renders ≥ 50 rows
4. Tap any judge
5. Verify judge profile loads (style preference bars, by_year, by_class)

**Assertions:**
- **No element has computed color `#D4AF37`** — pins the Pulse regression. Once gold is fully removed from the codebase, this assertion guards against re-introduction.
- No `console.error`.
- Judge profile renders within 3 s on a 4G throttled connection.
- Screenshot diff against a baseline (Playwright `toHaveScreenshot`). First run captures the baseline, subsequent runs flag visual regressions. Useful when Pulse changes are intentional but should be reviewed.

### Flow 3 — Guest scrolls 30+ search results without errors ★ catches the render-thrash class

**Why:** The search/filter path can return up to 400 rows. With no memoization (`04-performance.md §3`), this is the most likely path to surface a runtime bug or a perf cliff.

**Steps:**
1. `goto('/')`, dismiss guest
2. Type `volkanovski` (or any common fighter name) in search
3. Wait for results
4. Click "Show More Results" until the button disappears (paginating through `displayLimit`)
5. Vote on 3 fights (favorite, like, dislike)
6. Tap one fight, then back

**Assertions:**
- No `console.error` after each vote.
- Vote counter increments visibly (`getByRole('button', { name: /like/i })` text changes).
- Page doesn't lock up — keyboard input still responsive after voting.
- DOM node count is reasonable (`page.locator('*').count() < 5000`) — catches render-explosion.

## What I'd skip

- Auth + leaderboard rank flow — high setup cost, low blast radius until a real user complains.
- Live event flow — can't simulate ESPN realistically; the server-side `poll-live-fights` Edge Function plus the existing client logic is a separate testable surface (unit-test the Edge Function function directly).
- Multi-tab guest-conflict scenarios — interesting but rare in practice.

## Out-of-scope reminder

This file is a **recommendation**. Do not auto-write the Playwright script. The user reviews and decides whether to invest the setup time (Playwright install, browser binaries, GHA wiring) before any test code lands.
